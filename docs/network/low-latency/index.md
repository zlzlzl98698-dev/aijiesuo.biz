# 低延迟机场测速方法论：指标差异与 2026-08-11 批次边界

> **核心结论（Answer-First）**：几乎所有刚接触代理客户端的新手都会困惑：“为什么客户端测速显示某个节点只有 35ms，打开 Google 却要转圈 5 秒甚至直接超时？”原因在于默认或旧式客户端显示的往往是 **TCP Ping（只测到了国内中转入口）**，而真正决定网页打开速度的是 **TLS RTT / HTTPS Ping（端到端全链路真实响应）** 与 **晚高峰丢包率**。

## 四大测速核心指标技术对比

| 测速指标 | 实际测量的网络路径段 | 能否反映跨境段真实质量 | 常见误导与局限 |
| --- | --- | --- | --- |
| **ICMP Ping** | 本地终端 → 目标 IP（注意：域名可能只解析到国内入口 IP） | **基本不能** | 多数代理协议跑在 TCP/UDP 端口上，且许多中转机禁 Ping；即使通畅也与加密隧道转发无关 |
| **TCP Ping** | 本地终端 → 代理服务器端口完成 TCP 三次握手 | **不能（极易产生假绿灯）** | 在中转/专线机场中，TCP Ping 只测了“你到国内入口机”的延迟；即使国内入口到海外落地段断了，TCP Ping 照样显示 25ms |
| **TLS RTT / HTTPS Ping (URL-Test)** | 本地终端 → 入口 → 跨境隧道 → 海外落地机 → 真实海外目标（如 `cp.cloudflare.com` 或 Google `generate_204`）完成 TLS 握手与 HTTP 响应 | **能（最核心的延迟指标）** | 首次连接包含冷启动 TLS 握手，通常会比 TCP Ping 高 2–4 倍；但后续复用连接时接近真实网页首字节耗时 |
| **并发吞吐测速 (Speedtest)** | 测速客户端建立多线程或单线程向海外测试文件节点拉取数据（记录平均速度与峰值速度） | **能反映带宽上限，但受测试后端影响极大** | 机房 5Gbps/9Gbps 后端与家庭宽带差距大；高频并发测速会瞬间吃掉大量账户月流量配额 |

## 2026-08-11 实测批次方法论与技术透明度说明

在本站归档并公开的 `2026-08-11` 测速批次（详见 《2026-08-11 节点测速原始图像校验清单》 与 《2026-08-11 16家机场节点测速方法与边界说明》）以及 `2026-07` / `2026-08-19` 补充实测中，截图主要来自两套测试工具链：

1. **工具链 A：`MAI-TEST-BOT 2.0.0-dev`**（涵盖 2026-08-11 批次中 14 家 Shadowsocks 截图）
   - 典型测试条件：珠海联通 5Gbps 后端、32 线程并发、Ping 5 次；
   - 展示字段：节点名称、协议、RTT / HTTP 延迟、平均速度、最高速度、速度曲线与 UDP NAT 类型。
2. **工具链 B：`MiaoKo` 自定义测试（主端 4.3.3 / 喵速 4.7.0）**（涵盖快狸、宇宙云及微风、无忧、光速云 8/19 补充测试）
   - 典型测试条件：珠海联通 9Gbps 后端（单线程或 32 线程）或长沙电信/广西移动/河北联通 2Gbps 6 线程；
   - 展示字段：明确区分 **TLS RTT 与 HTTPS 延迟**、下载均速/峰值、UDP NAT 类型（FullCone / RestrictedCone / Unknown），以及在 `normalspeed` / `test` 模式下独立测试 Netflix、Disney+、YouTube、OpenAI、Gemini 解锁列。

### 引用这批方法论数据时必须牢记的 5 条边界
1. **单日快照属性**：2026-08-11 各品牌测试分布在凌晨（00:21–01:48）、白天（08:52–15:50）与晚间（18:45–22:46），时间窗口不一致，**不可直接做成绝对横向排名**。
2. **机房后端 ≠ 家庭宽带**：珠海联通 5G/9G 骨干网后端测出的 400–550MB/s 反映的是节点自身出口带宽潜力，普通家庭千兆宽带上限约为 100–120MB/s。
3. **异常值保留原则**：实测图中同时存在 `0B`、`1.60KB/s`、`43.08KB/s`、异常高延迟与 `UDP Unknown`，这些真实异常不得为美化结论而删除。
4. **速度不推导解锁**：纯测速图（`speed`）不能推导 ChatGPT/Gemini/Netflix 解锁状态，必须由包含独立检测列的快照证明。
5. **非机器原始日志**：存档均为 1122×1402 px PNG 截图，不含原始 JSON/CSV 明细，严禁通过目测估算不存在的聚合均值。

## 普通用户在本地如何正确测出“真低延迟”与“晚高峰丢包”

### 步骤 1：把客户端默认测速改成 `HTTPS URL-Test`
- 在 [Clash Verge Rev](/clients/clash-verge-rev/)、FlClash、Shadowrocket 等客户端的设置中，确认延迟测试地址为真实海外轻量化地址（如 `https://www.gstatic.com/generate_204` 或 `https://cp.cloudflare.com/generate_204`），切勿使用只测端口连通的纯 TCP Ping。
- 正常的端到端 HTTPS 延迟参考值：香港/台湾/日本/新加坡节点通常在 **120ms–350ms**（含首包 TLS 握手）即属流畅；若超过 **800ms–1500ms** 或直接 `Timeout`，说明跨境段拥塞严重。

### 步骤 2：避免频繁点击“全节点批量测速”
- 每次对 60–70 个节点跑并发速度测试，不仅可能消耗数 GB 流量，还会瞬间触发部分机场面板的并发连接风控。日常只需用 **URL-Test 测延迟** 即可，仅对选中的 1–2 个主力节点通过浏览器打开 YouTube 4K 测试实际码率稳定性。

### 步骤 3：自测晚高峰丢包与抖动（20:30–22:30 实测法）
1. 在本地终端开启 TUN 模式或走代理的连续探测（如通过 `curl -w "dns:%{time_namelookup} tcp:%{time_connect} tls:%{time_appconnect} ttfb:%{time_starttransfer}\n" -o /dev/null -s https://www.google.com/generate_204` 连续运行 10 次）。
2. 观察 `ttfb`（首字节返回时间）是否每次都稳定在相近区间；如果出现某几轮从 `0.25s` 突然跳到 `2.8s` 甚至超时，说明该节点在晚高峰存在明显微丢包或链路排队拥塞。

## 常见问题（FAQ）

### 为什么我的节点 HTTPS 延迟显示 260ms，但刷网页感觉很快，一点也不卡？
因为现代客户端执行 URL-Test 时测的是**冷启动建立一次完整 TLS 握手 + HTTP 请求的总耗时**（包含 2–3 个 RTT 往返）。当你正常用浏览器打开网页时，浏览器会复用已建立好的 TLS 连接（HTTP/2 或 HTTP/3 多路复用），后续资源的实际加载延迟只有几十毫秒，因此体感非常流畅。

### 测速图里的 `MB/s` 和运营商宽带说的 `Mbps` 怎么换算？
工程上 `1 MB/s = 8 Mbps`（字节与比特换算）。例如 100Mbps 家庭宽带的理论峰值下载速度约为 `12.5 MB/s`；而 《2026-08-11 16家机场节点测速方法与边界说明》 明确提醒：**若部分截图或文档未明确界定单位统计口径时，不得擅自替换原文数字**。

### 游戏玩家关心的“丢包率 0%”能用 Clash 测速看出来吗？
Clash 的单次 URL-Test 只发极少请求，测不出持续性 UDP 小包丢包率。游戏玩家需要进入游戏内查看实时网络图表（Packet Loss）或使用专业游戏测速工具验证 UDP 会话连续性，详见[低延迟游戏加速说明](/vpn/gaming/)。
